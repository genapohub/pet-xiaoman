# 宠小满 V1.0 开发复盘总结 v1.0

> 复盘日期：2026-09-15  
> 复盘范围：从单店 MVP 骨架到多租户白标 MVP / V1.0 试运营候选版  
> 复盘目的：沉淀可复用的产品、工程、验收和协作方法，服务后续 V1.1/V1.5/V2.0

## 一、结论先行

宠小满 V1.0 的核心经验不是“把模块做全”，而是建立了一个可验证的交付闭环：

```text
产品边界锁定
  -> 多租户与品牌契约
  -> C/B/API 同步实现
  -> 自动化门禁
  -> 真实门店数据演练
  -> C/B 双端回读
  -> 人工 UI/真机验收
  -> 项目台账与技能记忆沉淀
```

当前应继续定义为：**多租户白标 MVP / V1.0 试运营候选版**，不是 V2.0。

已形成的有效能力：

- C 端小程序：品牌入口、价格、预约、订单、宠物档案、个人中心、承诺页。
- B 端后台：工作台、订单履约、影像节点、客户、服务项目、商品、寄存、员工权限。
- 平台超管：开店、品牌白标、账号开通、门店启停、独立小程序入口配置。
- 多租户：`store_id` 数据隔离、`slug`/默认入口识别、C 端 `X-Store-Slug` 传递。
- 试运营证据：真实门店开通、店长登录、C 端换肤和一笔完整订单闭环。

仍未达到正式生产准入的事项：微信真机与真实账号复核、连续真实订单、正式支付、生产 MySQL/COS/HTTPS、提审资料和 Docker 发布仿真。

## 三、最重要的 8 条经验

### 1. MVP 的核心是验证命题，不是功能数量

宠小满的 MVP 命题是“一家真实门店能否完成从预约到交付的闭环”。多门店、白标、支付配置位等能力只有服务于这个命题才进入 V1.0；司机端、兽医协作、集团看板、会员储值和开放 API 暂不提前实现。

**可复用规则**：每新增一个模块，必须回答“它是否阻断当前验证命题”；不能回答就进入后续产品池。

### 2. 多租户必须是数据契约，不只是页面换肤

品牌色和 Logo 只是表象，真正的租户隔离要同时覆盖：

- 数据模型的 `store_id`。
- 入口识别的 `slug`、默认 AppID 和扫码参数优先级。
- C 端每个业务请求的 `X-Store-Slug`。
- B 端路径显式携带 `store_id`。
- 平台超管权限和租户角色的双重拦截。

**可复用规则**：任何新增业务接口必须在设计阶段写清“租户从哪里来、缺失时怎么办、跨租户如何拒绝”，不能只在前端传一个门店参数。

### 3. 状态流转要绑定副作用前置条件

订单不是简单改一个 status。宠小满把影像上传、支付结清、交付动作与状态机绑定，避免后台人员跳过服务证据直接完成订单。

**可复用规则**：状态机验收至少覆盖正常路径、前置条件缺失、重复操作、跨角色操作和异常恢复；每一步都要能在 C 端和 B 端回读到同一结果。

### 4. 自动化质量和真实运行质量必须分层表达

本项目经历了：后端测试、Python 编译、后台构建、小程序资源检查、API 健康检查、当前运行服务实测、真实门店演练、人工 UI 截图和真机门禁。它们分别证明不同事情，不能互相替代。

**质量四级**：

1. 代码通过：测试、编译、构建无错误。
2. 运行通过：服务启动、接口响应、资源可访问。
3. 业务通过：真实门店资料和真实订单完成闭环。
4. 生产通过：微信真机、正式三方配置、生产部署和回滚完成。

### 5. UI 验收要看真实内容和真实设备约束

预约页的问题不是静态代码能完全发现的：犬猫选择交互不够自然、固定提交栏遮挡明码标价、长内容和安全区影响可读性。通过微信开发者工具和浏览器截图才能发现这些问题。

**可复用规则**：小程序页面验收至少覆盖 320/375/414 宽度、长内容、键盘弹起、底部安全区、固定操作栏、空态/错误态/加载态和价格一致性。

### 6. 三方能力先配置化，避免阻塞 MVP

微信支付、地图、订阅消息等能力受商户号、域名、证书、模板 ID 和平台审核限制。V1.0 先保留到店付和人工兜底，同时把配置、状态查询、可用性提示做出来，比在缺少真实凭证时伪接更可靠。

**可复用规则**：三方集成必须有“关闭态、配置缺失态、调用失败态、正式启用态”四种状态，默认不能因为缺少密钥让主流程不可用。

### 7. 启动问题要给出可操作的诊断信息

“找不到 Python 解释器”和“代理 ECONNREFUSED”本质上是环境问题，不应只显示一个泛化错误。最终通过解释器检查、端口约定、`/healthz`、代理目标和启动顺序提示，降低了 PyCharm 手动启动成本。

**可复用规则**：启动脚本和前端代理报错必须回答：哪个服务、哪个地址、什么原因、下一步执行什么、如何验证恢复。

### 8. 真实数据演练是从 Demo 到产品的分水岭

使用 `chongxiaoman-pilot` 和订单 `GD20260915001` 完成真实门店资料、品牌、店长账号、影像、付款和订单状态闭环后，才真正知道系统是否能运行。测试夹具只能证明代码契约，不能证明产品可用。

**可复用规则**：每个 MVP 至少建立一条可重复的真实演练 SOP，并把订单号、租户、关键回读结果和未完成门禁写入文档。

## 四、哪些做法需要停止或改进

### 需要停止

- 把“后端测试通过”直接表述为“项目已上线”。
- 在没有真实商户号、地图 Key 或订阅模板时硬接三方服务。
- 只看后台页面，不看 C 端真实设备的长屏和安全区。
- 只按功能清单推进，不写明确不做和阶段进入条件。
- 把平台超管看全部数据等同于业务接口可以省略租户过滤。

### 需要改进

- 把 API 状态、UI 文案、冒烟脚本和产品文档维护成一套状态词典。
- 在新增业务接口时同步补跨租户、权限、空数据、失败重试和幂等测试。
- 在每次提交前固定执行“状态清理 → 测试 → 构建 → 运行实测 → 文档 → Git 边界检查”。
- 把人工验收证据从临时截图目录同步成项目内可追溯的验收记录。

## 七、复盘后的交付原则

> 下一阶段不靠功能更多进入，而靠上一阶段被验证进入。

对宠小满的执行顺序固定为：先修 P0 阻断，再做真实门店演练；先让一笔订单稳定闭环，再扩大订单数量；先把第三方做成可配置，再在凭证齐全后打开正式能力；先留下证据，再给阶段结论。
