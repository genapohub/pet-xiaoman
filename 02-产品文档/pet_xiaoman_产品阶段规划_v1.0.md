# pet_xiaoman（宠小满）产品阶段规划 v1.0

## 1. 结论

当前宠小满项目不应定义为 V2.0，建议定义为：

> **多门店白标 MVP 收口阶段 / V1.0 试运营候选版**

原因是：系统已经超过最初“单门店 MVP”的范围，提前实现了多门店租户、平台超管、白标换肤和 C/B 端主流程闭环；但它还没有完成真实生产环境上线、真实门店连续跑单、支付商户号接入、类目提审、人工冒烟和运营数据验证。因此它是“能力上接近 V1.0，验证上仍处于 MVP 收口”，不是 V2.0。

一句话口径：

> **宠小满现在是多租户白标 MVP，不是 V2.0；下一阶段目标不是继续堆功能，而是把它推进到 V1.0 试运营。**

## 2. 版本口径

| 口径 | 当前判断 | 说明 |
|---|---|---|
| PRD 文档版本 | v1.4 | 文档已反向同步多门店租户、平台超管、白标换肤 |
| 产品阶段 | MVP 收口 | 主链路已形成，但真实生产验证未完成 |
| 对外发布版本 | V1.0 RC | 可作为 V1.0 候选版进入试运营准备 |
| 是否 V2.0 | 否 | V2.0 应代表规模化 SaaS 能力，而不是仅提前做了多租户基础 |

## 3. 当前已具备的核心能力

### 3.1 C 端小程序

- 品牌首页、价格表、预约下单、收银台、预约成功、订单列表、订单详情、宠物档案、个人中心等主流程已基本闭环。
- 已支持按门店 `slug` 进入后换肤。
- C 端业务请求已携带 `X-Store-Slug`，后端按门店隔离数据。

### 3.2 B 端门店后台

- 今日工作台、订单管理、订单详情、服务项目、商品、客户、寄存、数据看板、员工与角色权限等门店履约模块已成型。
- 后台登录、员工角色、菜单权限、按钮权限已接入。
- 门店后台按登录员工所属门店隔离数据。

### 3.3 平台超管

- 平台管理员可开通门店、停用门店、配置门店品牌 UI、开通门店账号。
- 平台超管不进入租户履约页，避免无门店上下文造成脏数据。
- 门店详情已补充“小程序码 / C 端入口参数”展示入口。

### 3.4 多租户与白标

- 共享库共享表 + `store_id` 行级隔离已落地。
- 宠小满作为默认示例门店，`slug=chongxiaoman`。
- 新门店不继承宠小满品牌资产，只使用门店自身品牌资料。

## 4. 为什么不是 V2.0

V2.0 不应按“做了多租户”来判定，而应按“产品是否经过真实商业验证并进入规模化”来判定。

当前还没有满足 V2.0 的四个条件：

| V2.0 条件 | 当前状态 | 判断 |
|---|---|---|
| 真实生产环境稳定运行 | 未完成生产部署与迁移演练 | 不满足 |
| 至少 1 家真实门店连续跑单 | 待人工冒烟与试运营 | 不满足 |
| 核心业务指标有数据 | 暂无真实转化、加购、影像覆盖数据 | 不满足 |
| 商业化/平台化模型验证 | 支付、结算、平台看板、订阅收费未成型 | 不满足 |

所以当前正确阶段是：

> **MVP Plus / V1.0 RC，而不是 V2.0。**

## 5. 下一阶段产品目标

### 5.1 阶段目标

把宠小满从“能跑的 MVP”推进为“能给真实门店试运营的 V1.0”。

### 5.2 北极星指标

| 阶段 | 北极星指标 | 目标 |
|---|---|---|
| MVP 收口 | 主流程可人工跑通率 | 核心链路 100% 通过 |
| V1.0 试运营 | 月完成服务单量 | 先完成 10 单真实闭环 |
| V1.5 商业化 | 线上预约占比 | 新订单 60% 以上走小程序 |
| V2.0 平台化 | 多门店有效使用数 | 3 家以上真实门店持续使用 |

## 6. 未来三个版本规划

### 6.1 V1.0：真实门店试运营版

目标：让 1 家真实门店能稳定使用系统接单、履约、回访。

P0 范围：

| 模块 | 要做什么 | 验收口径 |
|---|---|---|
| 本地人工冒烟 | API、后台、小程序完整跑一遍 | 主流程无阻断错误 |
| 真实门店资料 | 使用真实店名、logo、服务价格、商品图 | C/B 端均展示正确 |
| 订单主链路 | 预约、确认、接宠、影像、交付、完成 | 1 单完整走通 |
| 小程序码入口 | 平台可复制 page/scene，C 端可按 slug 换肤 | 扫码或开发者工具路径能切品牌 |
| 生产部署准备 | 数据库迁移、上传目录、环境变量、备份方案 | 可按清单部署 |
| 合规准备 | 小程序类目、服务协议、价格声明、中性文案 | 提审材料齐备 |

V1.0 不做：

- 不做平台跨店经营看板。
- 不做租户自助入驻。
- 不做复杂装修系统。
- 不做平台收费订阅。
- 微信支付可作为开关能力，商户号未就绪时不阻塞上线。

### 6.2 V1.1：履约稳定版

目标：减少门店真实使用中的卡点，补齐异常处理和信任转化。

2026-09-13 执行状态：V1.1 中不依赖真实三方资质的能力已前置收口。C003 服务详情/科普、取消原因、C/B 端改期约束、服务端影像强校验、订阅消息配置入口、回访与来源标记均已进入当前版本。真实订阅推送依赖微信模板 ID，保持配置位。

建议范围：

| 功能 | 优先级 | 原因 |
|---|---|---|
| C003 服务详情/科普页 | P0 | 当前信任转化链路缺一页 |
| 订单改期状态约束 | P0 | 避免已完成订单被改时间造成数据失真 |
| B 端取消原因 | P0 | 店员/店长取消订单需要留痕 |
| 无影像流转例外 | P1 | 弱网或设备故障时不能卡死业务 |
| 订阅消息与提醒策略 | P1 | 让顾客感知服务进度 |
| 回访任务闭环 | P1 | 形成口碑与转介绍抓手 |

### 6.3 V1.5：支付与经营版

目标：从“记录系统”升级为“经营系统”。

2026-09-13 执行状态：V1.5 中可配置、可人工闭环的部分已提前落地。微信 JSAPI 支付框架、回调验签、幂等落账、到店付结清、退款任务人工闭环、支付渗透率/加购率/来源分布等经营指标已具备；真实支付商户号、地图服务和订阅模板仍按配置位开启，不阻塞 V1.0 试运营。

建议范围：

| 功能 | 优先级 | 原因 |
|---|---|---|
| 微信 JSAPI 支付 | P0 | 支持定金、全款、纪念品直购 |
| 支付回调与对账 | P0 | 避免支付状态与订单状态不一致 |
| 退款任务与退款状态 | P0 | 当前仅有退款中状态，未真正执行 |
| 来源渠道统计 | P1 | 验证小红书、转介绍、自然搜索效果 |
| 加购率与客单价看板 | P1 | 判断纪念品与寄存是否创造增量 |
| 服务项版本复盘 | P2 | 看价格调整对转化率影响 |

### 6.4 V2.0：多门店 SaaS 平台版

只有当 V1.0 试运营数据成立后，才进入 V2.0。

进入条件：

- 至少 1 家真实门店连续跑完 10 单。
- 新订单 60% 以上通过小程序预约。
- 影像节点覆盖率接近 100%。
- 店员能独立使用后台完成订单流转。
- 至少有 2 家潜在门店愿意试用同一套系统。

V2.0 范围：

| 模块 | 能力 |
|---|---|
| 平台经营看板 | 跨店订单、收入、活跃、异常、服务项表现 |
| 租户开通流程 | 更标准的开店、开号、品牌配置、初始化数据模板 |
| 套餐模板库 | 平台预设服务项目模板，新门店一键启用 |
| 白标增强 | 头图、承诺文案、门店电话、营业时间、资质图配置 |
| 商业化 | 门店订阅、按单抽成、套餐版本、账单管理 |
| 运维治理 | 门店数据导出、审计日志、异常监控、备份恢复 |

| 产品阶段命名 | 多租户白标 MVP / V1.0 RC | 既承认能力已超过单店 MVP，又避免误判成 V2.0 |

## 10. 阶段门禁

### MVP 收口进入 V1.0 的门禁

- API、后台、小程序本地均能稳定启动。
- 后端测试通过，后台构建通过，小程序静态检查通过。
- 至少 1 条真实门店配置完整：品牌、价格、商品、账号。
- C 端按门店 `slug` 换肤无串店。
- 一笔订单从预约到完成跑通。
- 明确小程序提审材料与支付开关状态。

### V1.0 进入 V1.5 的门禁

- 真实订单不少于 10 单。
- 90% 以上订单在系统内有完整服务记录。
- 店员能独立完成订单流转。
- 顾客能通过订单页理解服务进度。
- 明确支付商户号与回调配置。

### V1.5 进入 V2.0 的门禁

- 线上预约占比达到 60%。
- 至少 2 家门店进入试用意向。
- 服务项、订单、客户、影像、商品数据能稳定按门店隔离。
- 平台商业化方式明确：订阅、抽佣或系统交付费。

## 11. 一句话给后续协作

> 当前不要喊 V2.0；先把“多租户白标 MVP”打磨成可真实试运营的 V1.0，再用真实订单数据决定 V1.5 支付经营和 V2.0 SaaS 平台化。
