# pet_xiaoman（宠小满）MVP 迭代与 V2.0 / V3.0 产品规划 v1.1

## 1. 结论

结合智谱清言「宠物善终 C 端、B 端解决方案」沉淀内容，以及宠小满当前代码和文档进度，宠小满的产品路线应从“功能堆叠”切换为“阶段验证驱动”：

> MVP 不是再补一堆模块，而是把现有多租户白标能力跑成真实门店闭环；V2.0 不是因为功能多就叫 V2.0，而是因为多门店复制和商业化模型被验证；V3.0 才是开放平台、集团化、生态协作。

当前阶段仍定义为：

> **多租户白标 MVP / V1.0 试运营候选版**

下一步产品主线：

1. **MVP 迭代**：围绕真实门店试运营，把透明定价、预约、订单履约、影像追踪、回访、提审材料跑通。
2. **V1.5 经营增强**：等真实跑单后再打开微信支付、对账、退款、经营指标。
3. **V2.0 SaaS 平台化**：等至少 2-3 家门店愿意复制时，再做平台经营看板、模板库、白标增强、商业化收费。
4. **V3.0 生态扩展**：等多门店和商业化成立后，再做开放 API、集团管控、外部协作、跨区域能力。

本文 §4 给出以「MVP → V2.0 → V3.0」三段为主线的演进聚焦，§5–§14 为各阶段详细规划与指标支撑。

## 4. 三阶段演进主线（MVP → V2.0 → V3.0）

本节把前文的阶段总览收敛为一条**以验证驱动、层层设闸**的演进主线，作为整份规划的主心骨。三个阶段不是“功能多少”的划分，而是**商业验证深度**的划分：

- **MVP**：验证“单店真实闭环能不能跑起来”（产品可用）。
- **V2.0**：验证“门店能不能被标准化复制 + 商业模式是否成立”（可规模化）。
- **V3.0**：验证“行业协作与生态能不能成立”（平台化）。

每一阶段都有明确的**进入条件**与**退出条件**（见 §3 与 §11），未达标不跳阶段。

### 4.1 MVP 阶段：核心功能 / 用户场景 / 上线优先级

**产品定位**

> 多租户白标 MVP / V1.0 试运营候选版——不是再补模块，而是把现有能力跑成真实门店闭环。

一句话：先让“一家真实宠物善终门店”敢用宠小满完成从获客预约到服务完成的闭环。

**目标用户价值**

| 角色 | 价值 |
|---|---|
| C 端宠物主 | 价格透明、流程可追踪、不下单迷路、情绪被妥善安放（克制可靠的陪伴感） |
| B 端店员 | 新单进入工作台、状态流转清楚、影像可上传、节点不乱 |
| 平台 / 经营者 | 门店/订单/客户/商品/价格按 `store_id` 隔离不串店；试运营可复盘（来源/支付状态/加购/回访有入口） |

**核心功能与用户场景**

| 场景 | 用户故事 | 关键功能 | 优先级 |
|---|---|---|---|
| 获客与信任 | 宠物主刷到门店→看价格/服务→相信“不坑” | 首页、价格表、服务详情、关于承诺页；明码标价四处一致 | P0 |
| 预约下单 | 决定办理→手机填宠物/时间/地址→提交成功 | C 端预约下单、订单成功页、锁价说明 | P0 |
| 订单履约 | 店员收到新单→确认→接宠→服务中→影像→交付→完成 | B 端工作台、订单状态流转、影像上传 | P0 |
| 过程可解释 | 主人随时看“到哪一步了” | C 端订单时间线 + B 端影像节点 | P0 |
| 档案与寄存 | 登记宠物、查寄存状态 | 宠物档案、客户档案、寄存查询 | P1 |
| 多租户白标 | 不同门店用同一套系统、品牌各是各的 | slug 入口、换肤、品牌配置（店名/logo/主色/联系方式/小程序入口） | P0（平台侧已具备，本阶段做真实演练） |
| 提审准备 | 能提交小程序审核 | 类目、服务协议、隐私政策、价格说明、中性合规文案 | P0 |

**上线优先级（MVP 内部）**

| 优先级 | 事项 | 交付物 | 验收 |
|---|---|---|---|
| P0 | C 端二级页真机补截图 | 页面截图与问题清单 | 价格/详情/收银台/承诺页/订单详情无明显布局问题 |
| P0 | 真实门店资料演练 | 演练记录 | 店名/logo/主色/价格/商品/账号/默认入口正确 |
| P0 | 完整订单跑单 | 跑单记录 | 预约→确认→接宠→服务中→影像→交付→完成全链路走通 |
| P0 | 明码标价一致性验收 | 验收清单 | 首页/价格表/预约页/订单页价格表达一致 |
| P0 | 小程序提审材料补齐 | 提审材料清单 | 类目/协议/隐私/价格说明/中性文案齐备 |
| P1 | 异常场景脚本 | 冒烟脚本补充 | 取消/改期/影像失败/订阅失败/支付关闭均有兜底 |
| P1 | 回访任务口径 | 回访规则 | 订单完成形成回访待办或人工记录 |

**MVP 退出条件（进入 V1.0 试运营）**：C/B/API/小程序主链路无 P0 阻断；连续 10 单真实闭环、店员可独立操作。

**MVP 不做**：司机端 App、兽医协作端、数字纪念馆大模块、会员积分储值、平台订阅收费、开放 API、国际化——均放入后续阶段（见 §5–§14）。

### 4.2 V2.0 阶段：差异化功能 / 商业化探索

**产品定位**

> 多门店 SaaS 平台化——让新门店被标准化开通、初始化、配置品牌、复制服务模板，平台看得到多店经营表现。不是“多做几个功能页面”。

**目标用户价值**

| 角色 | 价值 |
|---|---|
| 新门店老板 | 30 分钟内完成基础配置开业；服务模板一键启用；品牌自主可控 |
| 平台运营 | 跨店经营看板、异常监控、模板沉淀、账单可收 |
| C 端客户 | 跨店一致的透明定价与服务体验 |

**差异化功能（相对单店工具）**

| 模块 | 功能 | 差异化点 | 优先级 |
|---|---|---|---|
| 平台经营看板 | 跨店订单/收入/活跃/异常/服务项表现 | 单店工具没有的全局视角 | P0 |
| 门店开通模板 | 开店向导、账号初始化、服务项模板、默认商品模板 | 把“开新店”从定制变标准动作 | P0 |
| 套餐模板库 | 平台预置服务套餐，新店一键启用可微调 | 多店复制的核心资产 | P0 |
| 白标增强 | 首页头图、承诺文案、营业时间、资质图、门店联系方式 | 在已有换肤上补经营要素 | P1 |
| 告别仪式轻量配置 | 仪式类型、主持人、鲜花/音乐/场地备注 | 先轻量，不碰复杂装修 | P1 |
| 会员 / 客户经营 | 客户标签、回访、转介绍、纪念品复购 | 把低频服务做出复购抓手 | P1 |

**商业化探索**

| 探索项 | 说明 | 优先级 |
|---|---|---|
| 商业模式选型 | 订阅 / 抽佣 / 系统交付费，至少先确定一种 | P0（进入前提） |
| 平台账单 | 门店套餐、到期提醒、账单记录 | P2 |
| 审计与导出 | 门店数据导出、操作日志、敏感操作审计 | P2 |

进入 V2.0 的前提（缺一不可）：至少 1 家门店完成 10 单以上、60% 新单来自小程序、店员独立使用、至少 2 家潜在门店愿试用、商业模式至少确定一种。

**迭代优先级**：P0 平台看板 / 门店开通模板 / 套餐模板库；P1 白标增强 / 告别仪式轻量配置 / 会员客户经营；P2 平台账单 / 审计导出。

**V2.0 验收**：新店开通 ≤30 分钟；服务模板复用率 ≥80%；多租户串店事故 0；看板数据 T+0/T+1；试用门店 30 天后仍持续使用。

### 4.3 V3.0 阶段：长期愿景 / 生态布局

**产品定位**

> 从“宠物善终 SaaS”升级为“宠物善终行业协作平台”，连接门店、集团、外部伙伴、数据与生态服务。

**目标用户价值**

| 角色 | 价值 |
|---|---|
| 集团 / 连锁 | 总部-区域-门店组织、跨店权限、合并报表 |
| 外部伙伴（医院/物流/纪念品供应商） | 通过开放 API / Webhook 接入，共享订单与数据 |
| 平台 | 数据智能（预测/投放效果/异常预警）、行业规范化合规档案 |

**长期愿景**

成为宠物善终行业的数字基础设施：不只服务于单店经营，而是把“门店履约能力 + 集团管控能力 + 供应链协作 + 行业合规”连成一张网，让新进入者低门槛接入、让成熟者跨店扩张。

**生态布局**

| 模块 | 功能 | 优先级 |
|---|---|---|
| 开放平台 | API Key、调用统计、接口文档、Webhook | P0 |
| 集团管控 | 总部-区域-门店组织、跨店权限、合并报表 | P0 |
| 中央调度 | 跨店订单分配、车辆/人员调度、异常提醒 | P1 |
| 供应链协作 | 纪念品供应商、库存、采购、交付记录 | P1 |
| 合规档案 | 资质、环保、防疫、服务记录留档 | P1 |
| 数据智能 | 服务预测、来源投放效果、异常订单预警 | P2 |
| 国际化 / 多区域 | 多语言、多币种、多时区 | P3（远期） |

进入 V3.0 的前提：至少 5 家持续活跃门店、稳定收入模型与付费门店、出现外部协作需求、数据治理（审计/备份/权限/导出）稳定。

**关键风险**：合规风险（只做资质留档与服务记录，不碰医疗诊疗结论）、数据安全（API/集团权限/跨店查询最小权限 + 审计）、平台复杂度（每个生态模块须有真实客户需求，不做演示型功能）、商业模式分散（优先订阅/交付费，抽佣谨慎验证）。

### 4.4 三阶段连贯路径小结

| 阶段 | 验证命题 | 北极星指标 | 闸门 |
|---|---|---|---|
| MVP / V1.0 | 单店闭环能不能跑 | 月完成服务单量 | 10 单真实闭环 |
| V1.5 | 系统能不能创造经营效率 | 线上预约占比 + 支付渗透率 | 支付/退款/对账稳定 |
| V2.0 | 门店能不能复制 + 模式成立 | 活跃门店数 | 2 家愿试用 + 商业模式确定 |
| V3.0 | 行业协作与生态能不能成立 | 平台协作订单占比 | ≥5 家活跃 + 外部协作需求 |

> 路线铁律：下一阶段不靠“功能更多”进入，而靠“上一阶段被验证”进入。凡未达闸门的功能（司机端、兽医协作、会员储值、开放 API、国际化等），一律放入对应阶段的产品池，不做演示型前置开发。

## 5. MVP 迭代规划

### 5.1 MVP 迭代目标

MVP 下一轮不是扩模块，而是把“能演示”变成“真实门店敢用”。

核心验收：

| 目标 | 验收口径 |
|---|---|
| 用户能放心下单 | 价格透明、承诺清楚、下单不迷路 |
| 店员能及时接单 | 新单进入工作台，订单列表可查，状态流转清楚 |
| 服务过程可解释 | C 端能看到状态，B 端能上传影像，节点不乱 |
| 数据不串店 | 门店、订单、客户、商品、价格按 `store_id` 隔离 |
| 试运营能复盘 | 来源、支付状态、加购、回访有记录入口 |

### 5.2 MVP 必做清单

| 优先级 | 事项 | 来源 | 交付物 | 验收 |
|---|---|---|---|---|
| P0 | C 端二级页真机补截图 | 当前 tracker | 页面截图与问题清单 | 服务价格、服务详情、收银台、承诺页、订单详情无明显布局问题 |
| P0 | 真实门店资料演练 | 当前 tracker + 外链上线清单 | 演练记录 | 店名、logo、主色、价格、商品、账号、默认入口正确 |
| P0 | 完整订单跑单 | PRD + 外链 V1.0 主链路 | 跑单记录 | 预约、确认、接宠、服务中、影像、交付、完成全链路走通 |
| P0 | 明码标价一致性验收 | 外链重点 + 当前 UI 问题 | 验收清单 | 首页、价格表、预约页、订单页价格表达一致 |
| P0 | 小程序提审材料补齐 | V1.0 上线前置 | 提审材料清单 | 类目、服务协议、隐私政策、价格说明、中性文案齐备 |
| P1 | 异常场景脚本 | 外链逐页异常场景 | 冒烟脚本补充 | 取消、改期、影像失败、订阅失败、支付关闭均有兜底 |
| P1 | 回访任务口径 | 外链运营指标 | 回访规则 | 订单完成后能形成回访待办或人工记录 |

### 5.3 MVP 不做清单

| 不做项 | 原因 | 放入阶段 |
|---|---|---|
| 司机端 App | 单店阶段 B 端后台足够，独立端会增加维护成本 | V2.0 后评估 |
| 兽医协作端 | 涉及医疗/安乐死合规，不适合 MVP 早期碰 | V3.0 前不做 |
| 数字纪念馆完整模块 | 情绪价值重要，但先用订单详情/承诺页轻量承载 | V1.5/V2.0 |
| 会员积分储值 | 善终低频，早做会偏离核心订单闭环 | V1.5 后验证 |
| 平台订阅收费 | 没有多门店付费验证 | V2.0 |
| 开放 API | 没有外部生态调用需求 | V3.0 |
| 国际化、多币种、多时区 | 与本地试运营无关 | V3.0 以后 |

## 6. V1.0 试运营规划

### 6.1 产品定位

V1.0 是“真实门店试运营版”，不是平台大版本。它的核心问题只有一个：

> 一家真实宠物善终门店能不能用宠小满稳定完成从获客预约到服务完成的闭环。

### 6.2 V1.0 范围

| 端 | 范围 | 说明 |
|---|---|---|
| C 端 | 首页、价格、服务详情、预约、订单、宠物档案、个人中心、承诺页 | 聚焦用户信任与下单 |

## 7. V1.1 履约稳定规划

### 7.1 产品定位

V1.1 解决真实使用中的卡点，不做平台扩张。

### 7.2 重点功能

| 功能 | 价值 | 触发条件 |
|---|---|---|
| 改期/取消规则细化 | 降低店员误操作和客户争议 | 试运营中出现改期/取消 |
| 影像上传弱网兜底 | 避免状态卡死 | 影像上传失败率超过 5% |
| 回访待办闭环 | 形成转介绍和口碑数据 | 完成订单超过 10 单 |
| 订阅消息真实模板 | 减少客户反复询问进度 | 微信模板 ID 就绪 |
| 服务详情/承诺页微调 | 提升信任转化 | 用户咨询高频问题稳定出现 |

### 7.3 V1.1 不做

| 不做项 | 原因 |
|---|---|
| 平台经营看板 | 真实多店数据不足 |
| 复杂仪式配置 | 可以先用服务项目和备注承载 |
| 积分/储值 | 与履约稳定无直接关系 |

## 8. V1.5 经营增强规划

### 8.1 产品定位

V1.5 是从“履约系统”升级为“经营系统”的阶段，核心是支付、对账和经营指标。

### 8.2 进入条件

| 条件 | 说明 |
|---|---|
| 真实订单不少于 10 单 | 有足够业务样本 |
| 店员能独立完成履约 | 支付不能掩盖履约问题 |
| 微信商户资料齐备 | 商户号、APIv3 密钥、证书、回调域名 |
| 小程序提审基本通过 | 支付能力依赖正式环境 |

### 8.3 功能范围

| 模块 | 功能 | 说明 |
|---|---|---|
| 微信支付 | 定金、全款、纪念品直购 | 商户号就绪后打开 |
| 回调对账 | 回调验签、幂等落账、定时对账 | 防止支付状态错乱 |
| 退款 | 接宠前退款、人工审核、退款状态 | 初期可人工闭环，逐步自动化 |
| 经营指标 | 支付渗透率、加购率、客单价、来源转化 | 证明系统创造经营价值 |
| 商品经营 | 纪念品直购和随单交付 | 不做购物车和快递物流 |

## 9. V2.0 产品规划

### 9.1 产品定位

V2.0 是“多门店 SaaS 平台化”，不是“多做几个功能页面”。

一句话目标：

> 让新门店可以被标准化开通、初始化、配置品牌、复制服务模板，并让平台看得到多店经营表现。

### 9.2 进入条件

| 条件 | 最低门槛 |
|---|---|
| 真实门店连续跑单 | 至少 1 家门店完成 10 单以上 |
| 新订单线上化 | 60% 以上新订单来自小程序 |
| 店员独立使用 | 店员不依赖开发者完成日常履约 |
| 多门店意向 | 至少 2 家潜在门店愿试用 |
| 商业模式 | 订阅、抽佣或系统交付费至少确定一种 |

### 9.3 V2.0 核心模块

| 模块 | 功能 | 优先级 | 来源 |
|---|---|---|---|
| 平台经营看板 | 跨店订单、收入、活跃、异常、服务项表现 | P0 | 当前平台化缺口 |
| 门店开通模板 | 开店向导、账号初始化、服务项模板、默认商品模板 | P0 | 外链多租户 + 当前白标能力 |
| 套餐模板库 | 平台预置服务套餐，新店一键启用后可微调 | P0 | 多店复制需要 |
| 白标增强 | 首页头图、承诺文案、营业时间、资质图、门店联系方式 | P1 | 当前白标升级 |
| 告别仪式轻量配置 | 仪式类型、主持人、鲜花/音乐/场地备注 | P1 | 外链 V2.0，先轻量 |
| 会员/客户经营 | 客户标签、回访、转介绍、纪念品复购 | P1 | 外链会员模块改造 |
| 平台账单 | 门店套餐、到期提醒、账单记录 | P2 | 商业化验证后做 |
| 审计与导出 | 门店数据导出、操作日志、敏感操作审计 | P2 | 运维治理 |

### 9.4 V2.0 不做

| 不做项 | 原因 |
|---|---|
| 开放 API | 生态伙伴未验证 |
| 国际化/多币种 | 本地多店阶段不需要 |
| 复杂中央调度 | 未形成跨店调度复杂度 |
| 兽医协作端 | 合规复杂度高 |
| 重型低代码装修 | 白标增强足够，完整装修系统太重 |

### 9.5 V2.0 验收指标

| 指标 | 目标 |
|---|---|
| 新店开通时间 | 30 分钟内完成基础配置 |
| 服务模板复用率 | 80% 新门店使用模板初始化 |
| 多租户串店事故 | 0 |
| 平台看板数据延迟 | 日常经营数据 T+0/T+1 可用 |
| 门店留存 | 试用门店 30 天后仍持续使用 |

## 10. V3.0 产品规划

### 10.1 产品定位

V3.0 是“生态与集团化”，只有当 V2.0 平台化被验证后才有意义。

一句话目标：

> 从“宠物善终 SaaS”升级为“宠物善终行业协作平台”，连接门店、集团、外部伙伴、数据与生态服务。

### 10.2 进入条件

| 条件 | 最低门槛 |
|---|---|
| 多门店规模 | 至少 5 家持续活跃门店 |
| 平台商业化 | 有稳定收入模型和付费门店 |
| 外部协作需求 | 出现医院、物流、纪念品供应商或集团客户接入需求 |
| 数据治理能力 | 审计、备份、权限、数据导出稳定 |

### 10.3 V3.0 核心模块

| 模块 | 功能 | 优先级 | 说明 |
|---|---|---|---|
| 开放平台 | API Key、调用统计、接口文档、Webhook | P0 | 连接外部系统 |
| 集团管控 | 总部-区域-门店组织、跨店权限、合并报表 | P0 | 面向连锁或加盟 |
| 中央调度 | 跨店订单分配、车辆/人员调度、异常提醒 | P1 | 有跨店履约需求后再做 |
| 供应链协作 | 纪念品供应商、库存、采购、交付记录 | P1 | 纪念品规模化后 |
| 合规档案 | 资质、环保、防疫、服务记录留档 | P1 | 行业规范化方向 |
| 数据智能 | 服务预测、来源投放效果、异常订单预警 | P2 | 建立在足够数据基础上 |
| 国际化/多区域 | 多语言、多币种、多时区 | P3 | 暂属远期 |

### 10.4 V3.0 关键风险

| 风险 | 处理 |
|---|---|
| 合规风险 | 先做资质留档和服务记录，不碰医疗诊疗结论 |
| 数据安全 | API、集团权限、跨店查询必须有审计与最小权限 |
| 平台复杂度 | 每个生态模块都必须有真实客户需求，不做演示型功能 |
| 商业模式分散 | 优先订阅/交付费，抽佣需谨慎验证 |
