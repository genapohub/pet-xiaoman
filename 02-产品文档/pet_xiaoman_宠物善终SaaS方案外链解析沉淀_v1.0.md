# pet_xiaoman（宠小满）宠物善终 SaaS 方案外链解析沉淀 v1.0

## 1. 结论

智谱清言「SaaS解决方案智能生成器」分享链接中的完整对话已读取。该方案对宠物善终行业的判断和宠小满当前 PRD 主线高度一致：透明定价、线上预约、服务过程可追踪、纪念品/寄存、门店后台履约、平台多租户管理，都是同一条业务主线。

但它给出的三阶段方案偏“通用 SaaS 全量蓝图”，包含司机端、兽医协作端、租户订阅、开放 API、集团管控、国际化等较重能力。按 `mvp-expert-team` 门禁裁决，当前不能把这些能力直接塞进宠小满 V1.0。宠小满仍应保持：

> 多租户白标 MVP / V1.0 试运营候选版。先跑真实门店闭环，再进入 V1.5 支付经营和 V2.0 平台化。

## 3. 外链方案内容结构

### 3.1 对话 1：宠物善终 SaaS 总方案

该轮输出了完整行业方案，核心内容包括：

| 模块 | 外链方案要点 |
|---|---|
| 行业判断 | 宠物善终属于宠物服务细分场景，核心价值是遗体处理、告别仪式、火化、纪念品与情绪服务 |
| 竞品参考 | 强调市场正在从“基础处理”转向“标准化、透明化、情绪价值” |
| 架构概览 | 三层三端：SaaS 中台、业务后台、用户端 |
| 多租户 | 每个租户有门店、账号、品牌、业务数据隔离 |
| V1.0 范围 | 宠物档案、预约订单、服务流程、支付流水、火化记录 |
| API 契约 | 宠物、预约、订单、支付、火化记录等核心接口 |
| 页面设计 | 给出 C 端、B 端和中台页面清单，并以预约详情页作为代表作 |

### 3.2 对话 2：V1.0 页面设计延续

## 4. 与宠小满当前实现的对齐情况

| 外链方案能力 | 宠小满当前状态 | 判断 |
|---|---|---|
| C 端预约入口 | 已有品牌首页、价格表、预约下单、订单成功页 | 已覆盖 |
| 明码标价 | 已有服务项目与商品展示，并近期修复底部提示遮挡 | 已覆盖，需继续真机验收 |
| 订单追踪 | 已有订单详情、状态时间线和影像节点 | 已覆盖 |
| B 端订单处理 | 今日工作台、订单列表、订单详情、状态流转已成型 | 已覆盖 |
| 价格配置 | 服务项目与商品管理已成型 | 已覆盖 |
| 客户与宠物档案 | C 端宠物档案、B 端客户/宠物记录已具备 | 已覆盖 |
| 骨灰寄存 | B 端寄存管理、C 端寄存查询已具备 | 已覆盖 |
| 多租户 | 平台门店、门店品牌、门店账号、数据隔离已具备 | 已覆盖 |
| 白标换肤 | C 端 slug / DEFAULT_STORE_SLUG / 独立 AppID 入口已支持 | 已覆盖 |

### 4.2 已提前做成“配置位”或“人工闭环”

| 外链方案能力 | 宠小满当前策略 | 裁决 |
|---|---|---|
| 微信支付 | 已有配置位、JSAPI 框架、回调验签思路；商户号未就绪时到店付 | V1.5 打开，不阻塞 V1.0 |
| 订阅消息 | 已有模板配置位；真实模板 ID 待微信侧配置 | V1.1/V1.5 继续验证 |
| 地图定位 | 已按配置化思路保留，不强依赖第三方 key | V1.0 可用手填兜底 |
| 数据看板 | 已有基础统计 | V1.0 不追求平台经营看板 |
| 回访与来源 | 已有来源/回访方向 | V1.1 做实 |

### 4.3 外链方案有价值但应延后

| 能力 | 延后原因 | 建议阶段 |
|---|---|---|
| 司机端 App | 当前单店人手少，B 端后台即可完成接送与影像记录 | V2.0 后视订单量决定 |
| 兽医协作端 | 涉及安乐死、医疗协作、合规资质，风险高 | V2.0/V3.0 再评估 |
| 告别仪式复杂配置 | 当前应先用服务项目和订单备注承载，不做复杂仪式装修 | V1.5/V2.0 |
| 会员、积分、储值 | 善终服务低频，真实复购弱，早做容易偏离主线 | V1.5 后看纪念品数据 |
| 租户订阅收费 | 需要真实门店愿付费验证 | V2.0 |
| 开放 API | 当前没有生态伙伴接入需求 | V3.0 |
| 集团管控、财务合并 | 需要多门店规模样本 | V3.0 |
| 国际化、多币种、时区 | 与郑州本地试运营无关 | 暂不做 |

## 5. MVP 专家团裁决

### 5.1 阶段裁决

| 阶段 | 裁决 |
|---|---|
| 当前阶段 | 多租户白标 MVP / V1.0 RC |
| 当前主线 | V1.0 试运营闭环，而不是新开 V2.0 模块 |
| 外链方案定位 | 作为中长期蓝图参考，不作为当前迭代范围 |
| 近期不变原则 | 支付、地图、订阅等三方能力保持配置化；真实资质就绪后再打开 |

### 5.2 V1.0 RC 需要吸收的内容

| 吸收项 | 对宠小满的落地动作 |
|---|---|
| 透明定价叙事 | 继续强化 C002 价格表、预约页底部明码标价、订单锁价说明 |
| 流程可见 | 人工冒烟重点检查订单状态、影像、C 端时间线 |
| 情绪服务表达 | 服务详情、关于承诺、预约成功页文案继续保持克制、可靠、陪伴感 |
| 合规提示 | 小程序提审材料中补“宠物善终/无害化处理/价格说明/隐私政策”的中性表述 |
| 上线清单 | 复用外链的灰度、熔断、回滚思路，纳入 V1.0 试运营验收 |

### 5.3 V1.1 需要吸收的内容

| 吸收项 | 对宠小满的落地动作 |
|---|---|
| 异常场景速查 | 为订单取消、改期、影像上传失败、订阅失败补更细验收用例 |
| 回访闭环 | 把服务完成 30 天回访做成店员日常待办 |
| 纪念内容运营 | 先不做“数字纪念馆”大模块，可先在订单详情/承诺页放轻量纪念说明 |

### 5.4 V1.5 需要吸收的内容

| 吸收项 | 对宠小满的落地动作 |
|---|---|
| 微信支付 | 商户号、APIv3、证书、回调域名齐备后，打开定金/全款/纪念品直购 |
| 经营指标 | 补支付渗透率、加购率、客单价、来源渠道转化 |
| 退款与对账 | 从人工闭环升级为自动退款/对账任务 |

### 5.5 V2.0 以后再考虑

| 能力 | 进入条件 |
|---|---|
| 平台经营看板 | 至少 1 家门店跑完 10 单，且有真实订单/支付/加购数据 |
| 租户模板库 | 至少 2 家门店开通演练，服务项目差异可以抽象为模板 |
| 白标装修增强 | 多门店真正需要不同首页图、承诺文案、资质图时再做 |
| 平台订阅/收费 | 至少 2 家潜在门店愿意试用或付费 |
| 中央调度 | 多门店、跨人员、跨车辆调度产生真实复杂度后再做 |
