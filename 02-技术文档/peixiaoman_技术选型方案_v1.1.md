# peixiaoman（宠小满）技术选型方案

## 1. 文档信息
- 版本：v1.1 · 2026-09-05 · tech-lead-guide × 张孟博（v1.0 + 品牌定名宠小满 + ADR-006 多租户）
- 输入：PRD v1.1（已定稿）；参照系：宠宝树项目同栈经验（FastAPI + 微信云托管 + 原生小程序，含支付回调验签、SQLite→MySQL 迁移踩坑史）
- 场景：场景一（0→1 技术体系搭建），按 OPC 原则裁剪——团队规划/技术雷达/招聘规划不适用一人公司，本文聚焦选型 + ADR + 架构 + 非功能指标

## 2. 业务与技术对齐

| PRD 业务特征 | 技术约束推导 |
|---|---|
| 单店，年订单 <1 万，影像 50GB/年 | 无并发压力，**容量不是决策因素**；成本与维护复杂度才是 |
| 微信支付（定金/全款）+ 订单状态机 | 支付回调可靠性 > 一切；对账要留流水 |
| 影像上传（照片/60s 视频）+ 客户端浏览 | 对象存储 + 免内网流量；视频格式兼容要处理 |
| 一人公司 + AI 编程协作 | 栈越少越好；选自己（和 AI）最熟的，不选最潮的 |
| 门店生意在线下延续 | 可用性要求中等：系统挂了门店照样接单（微信+纸质兜底），SLA 不必过度投入 |

**架构风格决策**：单体（FastAPI 单服务 + 模块化分层），**明确不做**微服务/K8s/消息队列/Redis/多端小程序框架——反光鲜检查逐条：无多团队（不需要微服务）、无 10+ 服务（不需要 K8s）、无超 1 秒异步任务（订阅消息由微信侧触达，无自建队列场景）。等任何一条变化时再引入，变化信号写进 ADR-001。

## 3. 技术选型（6 项决策）

### 3.1 后端框架：FastAPI ✅（ADR-001 附带确认）

| 维度(权重) | FastAPI | Flask | Django |
|---|---|---|---|
| 团队匹配(5) | 5（宠宝树已在用，AI 生成质量高） | 4 | 3 |
| 功能匹配(5) | 5（自动 OpenAPI 文档=知识地图接口协议自动产出） | 4（需 Flask-RESTX） | 5 |
| 生态(4) | 4 | 5 | 5 |
| 运维(3) | 4 | 4 | 3（重） |
| **加权** | **4.65** | 4.3 | 4.0 |

- **结论**：FastAPI + SQLAlchemy 2.0 + Alembic 迁移。理由：与宠宝树同栈，支付回调验签、云托管部署、migrate 脚本经验全部平移，零学习成本。
- **后悔场景**：如果未来需要重后台管理能力（Django Admin 级别的现成后台）——本系统 B 端是自建 Vue 后台，该场景不成立。

### 3.2 数据库：MySQL 8.0（云托管内置）✅（ADR-002）

| 维度(权重) | MySQL（云托管） | SQLite | PostgreSQL |
|---|---|---|---|
| 支付对账匹配(5) | 5（事务+行级锁+并发读写） | 2（写锁全库，店员上传与客户下单并发即互相阻塞） | 5 |
| 团队匹配(4) | 5（宠宝树已迁移 MySQL，ER 经验可复用） | 5 | 4 |
| 运维成本(4) | 5（云托管内置，自动备份，免装机） | 5（零运维但无备份） | 4（云托管内置 PG 需自购） |
| 成本(3) | 4（按量，单店月费用 <10 元） | 5（免费） | 3 |
| **加权** | **4.75** | 3.9 | 4.2 |

- **结论**：MySQL 8.0，直接用微信云托管自建 MySQL 服务。**不复用宠宝树"SQLite 起家后补 MySQL"的路径**——宠宝树踩过的坑（本地/线上数据库不一致、迁移脚本双跑）没理由再踩一遍，尤其本系统有支付流水，对账数据不容许 SQLite 的单写者模型。
- **后悔场景**：如果数据量超单实例（>50GB）——年订单 <1 万影像走 COS，DB 年增 <1GB，10 年内不成立。

### 3.3 B 端后台前端：Vue 3 + Element Plus + Vite ✅（ADR-003）

| 维度(权重) | Vue3 + Element Plus | React + Ant Design |
|---|---|---|
| 组件匹配(5) | 5（表格+抽屉+上传+日期选择全是 B 端高频件，与 PRD 20 页需求一一对应） | 5（Antd 同样全） |
| AI 编程产出质量(5) | 5（SFC 单文件结构清晰，AI 生成完整页面成功率高；中文文档丰富） | 4.5 |
| 团队匹配(4) | 4（无强偏好） | 4 |
| 生态(3) | 5 | 5 |
| **加权** | **4.8** | 4.6 |

- **结论**：Vue 3 + Element Plus + Vite + Pinia。决策权重不在框架优劣（两者都足够好），在**AI 协作产出效率**——本项目前端主要靠 AI 生成，Element Plus 的中后台组件与 PRD §5.6.3 布局骨架（Navbar+Sider+查询表格页）零适配成本。
- **后悔场景**：如果要招专业前端做复杂交互——单店后台无此场景。

### 3.4 C 端：原生微信小程序 ✅（ADR-004 附带确认）

- **结论**：原生小程序，复用宠宝树的 request 封装（自动解包 data）、组件规范、订阅消息接入经验。
- **不做** uni-app / Taro：本系统只上微信端（用户全是微信搜一搜+小红书导流来的），跨端框架的抽象层反而增加 AI 生成代码的调试成本。**后悔场景**：如果要上支付宝/抖音小程序——郑州单店，无此计划。
- 注意点：iOS 视频拍摄默认 HEVC 编码，小程序 video 组件可能不兼容——上传前用 `wx.compressVideo` 统一转 H.264（写进开发注意事项）。

### 3.5 部署与基础设施：微信云托管全托管 ✅（ADR-005）

| 维度(权重) | 微信云托管 | 腾讯云轻量服务器 | Vercel/Serverless |
|---|---|---|---|
| 小程序集成(5) | 5（云托管调用免鉴权/免备案/内网直连，支付回调天然可达） | 3（需配域名+备案+白名单） | 2（国内访问+备案问题） |
| 运维成本(5) | 5（免运维：扩缩容/备份/监控全托管，宠宝树已有 Dockerfile+deploy 清单可直接复制） | 3（自装机、自备份、自续证书） | 4 |
| 成本(4) | 5（按量计费，单店预估月费用 <30 元：API 托管 + MySQL + COS） | 4（轻量 ~100 元/月包年，闲置浪费） | 4 |
| B 端托管(3) | 4（后台静态文件可托管同环境） | 4 | 4 |
| **加权** | **4.85** | 3.4 | 3.1 |

- **结论**：全栈微信云托管——API 容器 + MySQL + COS（影像存储）+ 后台静态托管，一个控制台管完。宠宝树的 Dockerfile、container.config.json、部署清单直接复制改造。
- **Make vs Buy**：全部 Buy。自建机房/自管数据库/自搭影像服务在单店场景下没有一项成立。
- **后悔场景（供应商锁定，明确接受）**：云托管锁定 = 迁移需改部署配置（业务代码无锁定，FastAPI 标准容器）。单店系统接受此锁定，理由：月成本 <30 元、免运维收益远大于迁移成本；真要迁出时按标准 Docker 镜像迁任意云，工作量约 2 人天。

### 3.6 影像方案：COS + 前端压缩（并入 ADR-005）

- 照片：店员端上传 → 云托管临时密钥直传 COS（内网免流量费）→ 元数据落 `service_media` 表。
- 视频：上传前 `wx.compressVideo` 转 H.264（解决 iOS HEVC 兼容），限制 60s/50MB（PRD §5.2.2）；**一期不做服务端转码**（省转码费用与复杂度，手机直出 H.264 已满足小程序播放）。
- 容量：年 5000 单 × 10 影像 × 平均 2MB ≈ 100GB/年，COS 按量约 10 元/月，可接受。

## 4. 架构设计（C4 简版）

### 4.1 Context（系统上下文）

```
                    ┌─────────────┐
   宠物主 ────────→ │             │ ←──── 店员/店长
   （微信小程序）     │ peixiaoman │      （Web 后台，Chrome/Edge）
                    │  门店系统    │
                    └──┬───┬───┬──┘
                       │   │   │
            ┌──────────┘   │   └──────────┐
            ↓              ↓              ↓
      微信支付平台     微信订阅消息      COS 对象存储
      （JSAPI 支付）  （节点通知）      （影像文件）
```

### 4.2 Container（容器）

```
┌─ 微信云托管环境 ────────────────────────────────┐
│                                                │
│  ┌──────────────┐   ┌──────────────────────┐   │
│  │ API 服务      │──→│ MySQL 8.0            │   │
│  │ FastAPI 单体  │   │ （云托管内置，自动备份）│   │
│  │ · C 端 API    │   └──────────────────────┘   │
│  │ · B 端 API    │   ┌──────────────────────┐   │
│  │ · 支付回调    │──→│ COS 对象存储          │   │
│  └──────┬───────┘   │ （影像，内网直传）      │   │
│         │           └──────────────────────┘   │
│  ┌──────┴───────┐                              │
│  │ 后台静态托管   │  Vue3 构建产物                │
│  └──────────────┘                              │
└────────────────────────────────────────────────┘
     ↑ 小程序（原生）          ↑ 浏览器（店员/店长）
```

单体内部模块划分（一个服务内的分层，不是微服务）：`routes/`（c端+b端路由组）· `services/`（业务逻辑：订单状态机/支付/影像）· `models/` · `middleware/`（鉴权/支付验签/审计）——目录约定沿用宠宝树风格，AI 生成代码的结构一致性最高。

## 5. 非功能需求（量化）

| 维度 | 指标 | 说明 |
|---|---|---|
| 可用性 | 99.5%（月不可用 <3.6h） | 单店有线下兜底流程，不必追 99.9% |
| 性能 | API P95 <500ms；小程序首屏 <2s | 单店并发 <10，天然达标，不做压测优化 |
| 容量 | 支撑年 1 万单 / DB 10GB / COS 200GB | 3 年余量；超量信号 = 月单 >1500，届时再谈扩容 |
| 安全 | 支付回调验签 fail-check；手机号脱敏；状态回退/影像撤回审计日志；HTTPS 全链路 | 沿用 PRD §8.5 权限矩阵，RBAC 三角色 |
| 备份 | MySQL 每日自动备份保留 7 天；COS 版本控制关闭（影像不可变） | 恢复演练一次（上线前） |
| 可观测 | 云托管自带监控 + 支付对账任务每日跑 + 失败告警（微信云托管告警到微信） | 不自建 Prometheus（反光鲜检查） |

## 6. ADR 记录

### ADR-001: 单体架构（FastAPI 单服务 + 模块化分层）
**状态**：已接受
**背景**：单店系统，一名开发者 + AI 协作，年订单 <1 万。
**决策**：单个 FastAPI 服务，按 routes/services/models 分层；C 端与 B 端 API 同服务不同路由组。
**后果**：正——部署/调试/备份极简，AI 上下文集中；负——C/B 端耦合在一个进程，一处崩全崩。
**风险与替代**：进程崩溃影响全端——接受（云托管自动重启 + 门店线下兜底）。替代方案微服务/独立 BFF 均否决（反光鲜检查不通过）。**引入微服务的触发信号**：出现第二个门店且需要独立部署，或月单超 5000。

### ADR-002: MySQL 8.0（云托管内置），不走 SQLite 起家路径
**状态**：已接受
**背景**：有支付流水对账，店员上传与客户下单存在并发写；宠宝树 SQLite→MySQL 迁移踩过环境不一致坑。
**决策**：直接 MySQL 8.0（云托管自建），Alembic 管迁移，本地开发用 Docker MySQL 保持环境一致。
**后果**：正——事务与并发写天然正确、自动备份、开发/生产环境一致；负——本地开发需要 Docker（多一步环境准备）。
**替代方案**：SQLite（零运维但单写者模型不适合支付对账，且历史踩坑）；PostgreSQL（云托管内置选项成本更高，无 PG 特有需求）。

### ADR-003: B 端后台 Vue 3 + Element Plus + Vite
**状态**：已接受
**背景**：B 端 10 页全是查询表格/抽屉表单/上传组件，前端主要由 AI 生成。
**决策**：Vue3 + Element Plus + Vite + Pinia。
**后果**：正——Element Plus 组件与 PRD 页面需求一一对应，AI 生成 SFC 成功率高；负——若未来引入 React 背景协作者需适应（单店无此场景）。
**替代方案**：React + Antd（同等优秀，纯凭 AI 产出质量微弱优势选 Vue）——承认这是close call，差异不构成风险。

### ADR-004: C 端原生小程序
**状态**：已接受
**背景**：只上微信端；宠宝树有 request 封装/组件规范/订阅消息经验。
**决策**：原生开发，复用宠宝树封装与规范。
**后果**：正——零抽象层成本，AI 生成直出可用代码；负——多端扩展需重写（接受，无多端计划）。
**替代方案**：uni-app/Taro（跨端能力浪费在只有微信端的场景，且增加 AI 生成代码的调试面）。

### ADR-005: 微信云托管全托管（API + MySQL + COS + 静态托管）
**状态**：已接受
**背景**：免运维、按量付费、小程序生态无缝（免鉴权域名/内网直传）、宠宝树部署资产可复制。
**决策**：全栈上微信云托管；影像直传 COS（临时密钥）；接受供应商锁定。
**后果**：正——月基础设施成本预估 <40 元、零装机运维、支付回调天然可达；负——锁定（迁移成本约 2 人天，业务代码无锁定）；依赖微信云平台稳定性。
**替代方案**：腾讯云轻量（月 ~100 元固定成本 + 自运维，无优势）；Vercel（国内备案/访问问题，否决）。

## 7. 工程约定（简）

- **仓库结构**：沿用宠宝树模式——`peixiaoman/04-前后端代码/` 下三个独立 git 仓库：`goodend-api`（FastAPI）、`goodend-miniapp`（原生小程序）、`goodend-admin`（Vue3 后台）。根仓库（治理件+文档）由 install.sh 已建，嵌套仓库自动隔离。选 Polyrepo 不选 Monorepo：与宠宝树一致、install.sh 隔离机制现成、单人开发多仓库成本可忽略。
- **分支策略**：Trunk-Based 简化版——`master`（保护）+ 短命 feature 分支 + AI 产出必须走分支 + 人类 review 合并（AGENTS.md 红线）。
- **质量门禁**：ruff（lint+format）+ pytest（核心状态机/支付逻辑必须有测试，PRD AC 直接转用例）+ `git-secrets`（密钥扫描）——对应 evals 基线三件套。
- **API 规范**：FastAPI 自动 OpenAPI 文档即接口协议（知识地图自动产出），路径风格 `/api/c/*`（客户端）/`/api/b/*`（后台）。

### ADR-006: 多租户——共享库共享表 + shop_id 行级隔离（**已推迟 Deferred**）
**状态**：推迟（2026-09-05 决策：先实现单门店定位）
**背景**：系统未来会给郑州多家善终门店使用（后台多租户），且小程序端需支持客户门店品牌 UI 定制装修；但当前优先把单门店主链路跑通。
**决策**：当前版本**不引入 shop_id**（YAGNI）；多租户完整方案（共享库共享表 + shop_id 行级隔离 + 邀请制人工开通 + 平台管理员角色）已设计并存档于 PRD §12.2，待触发条件满足后启用。启用时一次性加列回填，单店数据量小（年 <1 万单），回填成本秒级。
**启用触发信号**：① 自营店月单稳定 + 有同行门店表达使用意向；② 或小程序品牌装修需求立项（白标依赖多店）。
**后果**：正——当前版本最简，无隔离纪律负担；负——未来启用时需一次性改造（预估 +2 周，方案已存档不返工）。

|---|---|---|---|

| 单人开发进度风险 | 中 | 中 | MVP 聚焦 20 页 P0；AI 编程 + evals 基线保证质量；每任务走 Harness 闭环 |

- **backend-dev-guide**：按 ADR-001/002 建 `pxm-api`（单店版；ADR-006 启用时再加 shop_id，Model 设计避免硬编码门店信息即可）——模块顺序：订单状态机 → 支付（含对账任务）→ 影像上传 → 价格版本 → 寄存/回访；PRD §7.1 字段即建表基线。
- **frontend-dev-guide**：`pxm-miniapp` 按宠宝树 request 封装起步（入口带 shop 参数）；`pxm-admin` 用 Element Plus 布局骨架（Navbar+Sider）起模板，登录态绑定门店。
- **qa-testing-guide**：PRD 各功能 AC（Given/When/Then）直接转测试用例；支付回调/状态机回退/影像上传失败三处必测。
- **devops-guide**：宠宝树 Dockerfile + deploy 清单复制改造；上线演练含备份恢复一次。

## 10. 去AI味自检

- ✅ **不做决策**：不做微服务/K8s/Redis/消息队列/跨端框架/服务端转码——每项对应反光鲜检查一条，触发信号写进 ADR-001
- ✅ **数字具体**：SLA 99.5%（<3.6h/月）、P95 <500ms、年 1 万单/100GB、月基础设施 <40 元、迁移成本 2 人天
- ✅ **竞品立场**：对宠宝树是"复用踩坑经验而非复制路径"——同栈复用 70%，但 SQLite 起家路径明确不走（ADR-002）
- ✅ **此刻合理性**：单店年单 <1 万，过度设计的利息是一人公司的维护时间；每个"不做"都有重新引入的触发信号
- ✅ **优先级倾斜**：开发顺序倾斜主链路（订单状态机→支付→影像），P2 看板最后；ADR-003 承认 Vue/React 是 close call，不伪装成必然
